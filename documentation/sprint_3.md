## BE-1: Retry генерации FileId при коллизиях

### Пользовательская история
Как разработчик, я хочу иметь механизм повторной генерации FileId при коллизиях, чтобы гарантировать уникальность идентификатора файла даже в редких случаях совпадения UUID.

### Упрощения Спринта 3
- Максимум 3 попытки генерации
- Без использования специализированных библиотек retry (Spring Retry не подключается)
- Логирование каждой попытки в консоль

### Техническое задание
- В `UploadFileUseCase.uploadFile()` добавить цикл с максимум 3 итерациями
- На каждой итерации:
    - Генерировать новый `FileId` через `FileId.generateNewRandomUUID()`
    - Проверять существование через `metadataRepo.existsById(fileId)`
    - Если не существует — создавать файл и выходить из цикла
    - Если существует — логировать коллизию и переходить к следующей итерации
- Добавить метод `existsById(FileId)` в интерфейс `FileMetadataRepository` и его JPA-адаптер
- После 3 неудачных попыток выбрасывать `RuntimeException` с понятным сообщением
- Добавить логирование через `org.slf4j.Logger`

### Критерии приёмки
- При нормальной загрузке файла создаётся с первой попытки
- При искусственно созданной коллизии (мок в тесте) — файл создаётся со второй попытки
- После 3 неудачных попыток выбрасывается исключение
- В логах видны записи о каждой попытке генерации
- Все существующие тесты на загрузку файла проходят

### Оценка
0.5 дня

## BE-2: SHA256 дедупликация файлов

### Пользовательская история
Как пользователь, я хочу, чтобы система не сохраняла одинаковые файлы в хранилище повторно, чтобы экономить место в S3 и ускорять загрузку.

### Упрощения Спринта 3
- Дедупликация работает только для файлов менее 5 МБ (для больших файлов хэш не считается, чтобы не блокировать поток)
- При совпадении хэша — файл в S3 не перезаписывается, но в БД создаётся новая запись с ссылкой на тот же storageKey
- Без фонового процесса очистки "осиротевших" файлов (это на потом)

### Техническое задание
- Добавить зависимость `commons-codec` или использовать встроенный `java.security.MessageDigest` для SHA256
- Создать утилитный класс `Sha256Calculator` с методом `calculate(InputStream) -> String`
- В `UploadFileUseCase`:
    - Для файлов < 5 МБ вычислять SHA256 из `command.content()`
    - Проверять через `metadataRepo.findBySha256(sha256)` наличие файла с таким хэшем
    - Если найден — использовать его `storageKey` и `eTag`, не загружая в S3 повторно
    - Если не найден — загружать в S3 как обычно и сохранять хэш
- Добавить поле `sha256` в `FileRecordEntity` (уже есть в домене)
- Добавить метод `findBySha256(String)` в репозиторий
- Обновить `FileMetadata.markReady()` — принимать sha256 как обязательный параметр

### Критерии приёмки
- При загрузке двух одинаковых файлов второй не создаёт новую запись в S3 (проверка через MinIO Console)
- В БД создаются две разные записи метаданных, но с одинаковым `storageKey` и `sha256`
- Оба файла корректно скачиваются
- Файлы более 5 МБ загружаются без вычисления хэша (sha256 = null)
- Покрытие unit-тестом с моком S3-порта

### Оценка
1 день

## BE-3: Liquibase для управления схемой БД

### Пользовательская история
Как разработчик, я хочу использовать Liquibase для управления схемой базы данных, чтобы миграции были версионированы, воспроизводимы и безопасны для продакшена.

### Упрощения Спринта 3
- Переносим только текущую схему (одна таблица `file_metadata`)
- Без разделения на changelog-файлы по фичам (один master + один initial)
- Отключаем `hibernate.ddl-auto=update` только после успешного применения миграции

### Техническое задание
- Добавить зависимость `org.liquibase:liquibase-core` в `pom.xml`
- Отключить автоматическое создание схемы Hibernate: `spring.jpa.hibernate.ddl-auto=none`
- Создать структуру:
    - `src/main/resources/db/changelog/db.changelog-master.yaml`
    - `src/main/resources/db/changelog/changes/001-initial-schema.yaml`
- В `001-initial-schema.yaml` описать:
    - Создание таблицы `file_metadata` со всеми колонками (id, owner_id, original_name, storage_key, media_type, size_bytes, sha256, etag, status, created_at, updated_at, deleted_at, version)
    - Первичный ключ, индексы (по owner_id, sha256)
- В `db.changelog-master.yaml` подключить `001-initial-schema.yaml`
- Настроить в `application.yml`:
  spring:
  liquibase:
  change-log: classpath:db/changelog/db.changelog-master.yaml
- Удалить старые данные в БД перед первым запуском (liquibase создаст таблицу с нуля)
- Добавить запись в databasechangelog о применённой миграции

### Критерии приёмки
- При запуске приложения на чистой БД таблица создаётся через Liquibase
- В таблице databasechangelog есть запись о применённом changeset
- Hibernate НЕ создаёт и НЕ изменяет схему (ddl-auto=none)
- Приложение работает корректно: CRUD операции выполняются
- Откат миграции через liquibase rollback работает (проверка через CLI)

### Оценка

## BE-4: Мягкое удаление файлов (Soft Delete)

### Пользовательская история
Как пользователь, я хочу, чтобы при удалении файл помечался как удалённый, а не стирался физически, чтобы иметь возможность восстановить его в случае ошибки.

### Упрощения Спринта 3
- Физическое удаление из S3 не происходит (файл остаётся в хранилище)
- Удалённые файлы не отображаются в списке GET /api/v1/files
- Механизм восстановления (restore) не реализуется — только пометка
- Очистка "осиротевших" файлов из S3 — отдельная задача на потом

### Техническое задание
- В `DeleteFileUseCase.execute()` изменить логику:
    - Вместо `metadataRepo.deleteFile(fileId)` вызывать `metadataRepo.markAsDeleted(fileId)`
    - Устанавливать `deletedAt = Instant.now()`
    - НЕ вызывать `fileStoragePort.deleteObject()` (файл остаётся в S3)
- В `JpaFileMetadataRepositoryAdapter`:
    - Добавить метод `markAsDeleted(FileId)` — точечное обновление поля `deleted_at`
    - Изменить `findAll()` / `findAllByOwnerId()` — добавить фильтр `WHERE deleted_at IS NULL`
    - Изменить `findById()` — возвращать null/empty, если `deleted_at IS NOT NULL`
- В `FileMetadata` доменном объекте:
    - Добавить метод `markDeleted()` — устанавливает `deletedAt` и меняет статус
- Добавить интеграционный тест: после soft-delete файл не возвращается через GET

### Критерии приёмки
- DELETE /api/v1/files/{id} возвращает 204
- После удаления GET /api/v1/files не возвращает удалённый файл
- В БД запись остаётся, поле `deleted_at` заполнено
- Физически файл в MinIO не удаляется
- Повторный DELETE того же файла возвращает 404 (так как findById не находит)
- Все существующие тесты на удаление проходят после адаптации

### Оценка
1 день

## BE-5: Обработка ошибок API

### Пользовательская история
Как разработчик, я хочу иметь единую точку обработки ошибок API, чтобы клиенты получали понятные JSON-ответы вместо стектрейсов Spring.

### Упрощения Спринта 3
- Обрабатываем только 3 типа ошибок: NotFound, BadRequest, InternalError
- Без детализации по кодам ошибок (errorCode) — только message
- Без логирования каждого 400 в отдельный файл (только через стандартный logger)

### Техническое задание
- Создать пакет `org.example.file_manager_cloudflare.common.exception`
- Создать кастомные исключения:
    - `FileNotFoundException extends RuntimeException`
    - `InvalidFileNameException extends RuntimeException`
    - `FileStorageException extends RuntimeException`
- Заменить все `throw new RuntimeException("...")` в UseCase на соответствующие кастомные исключения
- Создать `@RestControllerAdvice` класс `GlobalExceptionHandler`:
    - `@ExceptionHandler(FileNotFoundException)` → 404
    - `@ExceptionHandler(InvalidFileNameException)` → 400
    - `@ExceptionHandler(Exception)` → 500 (fallback)
- Формат ответа:
  {
  "status": 404,
  "error": "File not found",
  "message": "File with id '...' not found",
  "timestamp": "2026-10-30T12:00:00Z"
  }

### Критерии приёмки
- При ошибке 404 возвращается JSON с понятным сообщением
- При ошибке 400 возвращается JSON с описанием проблемы
- При внутренней ошибке 500 возвращается общий JSON без стектрейса
- Все существующие тесты проходят после замены RuntimeException на кастомные исключения

### Оценка
1 день
