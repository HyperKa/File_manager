# Отчёт по практическому заданию №1
## Тема: Клиент-серверное веб-приложение по методологии 12 факторов

---

## 1. Доменная область приложения

Приложение представляет собой **сервис объектного файлового хранилища (Cloud File Manager)**.
Сервис предназначен для безопасной загрузки, хранения, управления метаданными и скачивания файлов пользователей с разграничением прав доступа.

В качестве основного хранилища бинарных данных используется S3-совместимое объектное хранилище (локально — MinIO, в облачном окружении — Backblaze B2), а метаданные файлов индексируются и сохраняются в реляционной СУБД PostgreSQL.

### Реализация CRUD-операций:
* **Create (C):** `POST /api/v1/files` — загрузка бинарного содержимого файла через multipart/form-data, потоковое вычисление хэша SHA-256 и сохранение в S3 с фиксацией метаданных в БД.
* **Read (R):**
    * `GET /api/v1/files` — получение пагинированного списка файлов текущего пользователя.
    * `GET /api/v1/files/{id}/content` — потоковое скачивание содержимого файла из S3-хранилища (`StreamingResponseBody`).
* **Update (U):** `PATCH /api/v1/files/{id}` — обновление метаданных сущности (переименование файла).
* **Delete (D):** `DELETE /api/v1/files/{id}` — удаление объекта из S3 и перевод статуса сущности в БД в состояние `DELETED`.

## 2. Стек реализации

* **Бэкенд:**
    * Язык: Java 25
    * Платформа: Spring Boot 3 (Spring Web, Spring Security, Spring Data JPA)
    * База данных: PostgreSQL 16
    * Управление миграциями: Liquibase
    * Клиент хранилища: AWS Java SDK v2 (`S3Client`)
    * Протокол взаимодействия: HTTP/1.1 (REST API, ProblemDetail по стандарту RFC 7807)
* **Фронтенд:**
    * Стек: React, TypeScript, Vite
    * Стилизация: Tailwind CSS (цветовая палитра: Zinc/Amber/White)
* **Инфраструктура и окружение:**
    * Docker & Docker Compose (контейнеры PostgreSQL и MinIO)
    * S3-провайдеры: MinIO (локально) / Backblaze B2 (облако)

## 3. Основные сущности доменной области

Основной агрегат системы — **`FileRecordEntity` / `FileMetadata`** (таблица `file_metadata`):
* `id` (`UUID`) — первичный ключ, глобальный публичный идентификатор файла.
* `ownerId` (`UUID`) — идентификатор пользователя/владельца файла (мультиарендность и безопасность доступа).
* `originalName` (`String`) — пользовательское имя файла, отображаемое в интерфейсе.
* `storageKey` (`String`) — внутренний детерминированный ключ объекта в бакете S3 (изолирован от клиентского ввода во избежание Path Traversal).
* `mediaType` (`String`) — валидированный MIME-тип файла.
* `sizeBytes` (`long`) — размер файла в байтах.
* `sha256` (`String`) — контрольная сумма файла для верификации целостности.
* `etag` (`String`) — ETag объекта, сформированный хранилищем S3.
* `status` (`Enum: PENDING, READY, FAILED, DELETING, DELETED`) — статус жизненного цикла сущности в процессе загрузки и удаления.
* `createdAt`, `updatedAt`, `deletedAt` (`Instant`) — временные метки аудита.
* `version` (`long`) — версионирование для механизма оптимистических блокировок (`@Version`).

## 4. Аргументация соответствия методологии 12 факторов (The Twelve-Factor App)

### I. Кодовая база (Codebase)
> *Одна кодовая база, отслеживаемая в системе контроля версий, множество развёртываний.*
* Проект хранится в едином Git-репозитории. Один и тот же код разворачивается в локальном dev-окружении и в продакшене. Разница между развёртываниями регулируется исключительно внешними конфигурациями и Spring-профилями (`local`, `prod`).

### II. Зависимости (Dependencies)
> *Явное объявление и изоляция зависимостей.*
* Все зависимости бэкенда строго зафиксированы в `pom.xml` (Maven), а фронтенда — в `package.json` и `package-lock.json`. Системные неявные зависимости отсутствуют.

### III. Конфигурация (Config)
> *Сохранение конфигурации в переменных окружения.*
* Все переменные параметры (подключение к БД, порты, ключи доступа к S3/Backblaze, токены безопасности) передаются через переменные окружения (`.env`, Docker Compose environment). В коде отсутствуют захардкоженные секреты.

### IV. Сторонние службы (Backing services)
> *Сторонние службы рассматриваются как подключаемые ресурсы.*
* СУБД PostgreSQL и объектное хранилище (MinIO / Backblaze B2) являются внешними подключаемыми ресурсами. Переключение с локального MinIO на облачный Backblaze B2 осуществляется сменой URL и ключей в конфигурации без модификации и перекомпиляции кода.

### V. Сборка, релиз, запуск (Build, release, run)
> *Строгое разделение стадий сборки и запуска.*
* Стадия сборки (`mvn clean package`, `npm run build`) формирует неизменяемые артефакты (JAR-файл и статический бандл). На этапе релиза артефакт объединяется с переменными окружения, после чего запускается.

### VI. Процессы (Processes)
> *Выполнение приложения как одного или нескольких процессов без сохранения состояния (stateless).*
* Серверная часть полностью stateless (`SessionCreationPolicy.STATELESS`). Пользовательские сессии не хранятся в памяти приложения. Все состояние персистентно сохраняется в PostgreSQL и S3. Любой экземпляр бэкенда может перезапуститься без потери клиентских данных.

### VII. Привязка портов (Port binding)
> *Экспорт служб через привязку к портам.*
* Приложение не требует стороннего веб-контейнера (Tomcat/WildFly) и само связывается с сетевым портом (8080 для бэкенда через встроенный сервер Spring Boot, 5173 для фронтенда Vite).

### VIII. Параллелизм (Concurrency)
> *Масштабирование за счёт модели процессов.*
* Благодаря отсутствию внутреннего состояния (stateless-архитектура) бэкенд легко масштабируется горизонтально: можно запустить любое количество идентичных инстансов сервиса за балансировщиком нагрузки (Nginx/HAProxy).

### IX. Утилизируемость (Disposability)
> *Максимизация надёжности за счёт быстрого запуска и корректного завершения работы.*
* В приложении включен режим плавного завершения работы (`server.shutdown: graceful`). При получении сигнала `SIGTERM` сервер завершает активные запросы ввода-вывода и закрывает транзакции перед остановкой процесса.

### X. Паритет окружений (Dev/prod parity)
> *Окружения разработки, тестирования и продакшена должны быть максимально похожи.*
* В качестве БД на всех этапах используется PostgreSQL (через Docker Compose локально). Для хранилища используется единый стандартизированный протокол Amazon S3 API (MinIO локально и Backblaze B2 в облаке), что исключает расхождение в поведении драйверов и клиентов.

### XI. Логи (Logs)
> *Логирование как поток событий.*
* Приложение не пишет логи в файлы внутри контейнера. Логи направляются потоком событий в стандартный вывод (`stdout`/`stderr`), откуда могут перехватываться Docker, systemd или сборщиками логов (ELK/Fluentbit).

### XII. Процессы администрирования (Admin processes)
> *Запуск задач администрирования и управления как разовых процессов.*
* Миграции схемы базы данных оформлены декларативно через Liquibase (`db.changelog.sql`) и выполняются автоматически при старте сервиса либо как отдельная разовая задача (`mvn liquibase:update`).
